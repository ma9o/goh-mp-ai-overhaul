# Static trace from decision inputs to orders

Further static analysis is productive before runtime work. This pass connects
the previously unnamed inputs to a subject-score calculation, ties the bounded
scalar to a named morale processor, and follows a state consumer into concrete
movement orders. All analysis uses the installed build 25492057 fingerprints;
the game and GEM were not launched.

The reproducible address map is [flow-map.json](../artifacts/build-25492057/flow-map.json).
Role names remain analyst descriptions unless explicitly tied to RTTI or strings.

Follow-up: [combat estimates and cover selection](tactics-map-25492057.md)
identifies P/Q's Human/Tank channels, their configuration and cache producer,
and the cover-scoring, rejection and rank-selection rules below this trace.

## How the missing producer was found

`FindMemberAccesses.java` scans Ghidra's existing instructions for literal
memory displacements, records operand read/write classification and containing
functions, and leaves the program unchanged. It examined 3,851,164 game
instructions and 3,411,642 editor instructions. The seven requested offsets
produced 480 and 405 leads respectively, including unrelated objects and stack
slots. These are leads, not automatically identified brain accesses.

The important result was **code without a Ghidra function object** at game
`0x944DE0`, with the same five-instruction bridge at editor `0x7CC2E0`:

```text
R8  = address of brain+0x518       # output A
RDX = address of brain+0x51C       # output B
RCX = brain->owner_actor->component_at_0xDD0
tail jump to game 0x877170 / editor 0x6FAE20
```

Both bridges also lack unwind entries. They were independently disassembled
with LLVM; their exact bytes are recorded in the manifest. This shows why
searching only exported functions and unwind records misses useful code.

Human primary slot 23, game `0x941BC0`, conditionally constructs a callback
pointing to `0x944DE0` at `0x941C9F` and passes it to `0xA19450` at
`0x941CD3`. This establishes a registration path. It does not yet establish
the callback's timing, thread, or ordering relative to reconsideration.

## What A and B actually calculate

The shared producer builds a self record using RTTI-named **`Actor::eSubject`**,
then visits two lists in the owner's component. The calculation is the same
in the reviewed game and editor bodies. It uses two-component values, subject
positions, a range-like value, timestamps, and classification flags.

Let `P(subject)` be the two floats at subject `+0x48/+0x4C` and `Q(subject)`
the two at `+0x54/+0x58`. The pair helper, game `0x8129D0`, computes:

```text
ratio_component(p, q) = p/q if q >= float32(0.1), otherwise 10
R(P, Q) = min(ratio_component(P.x, Q.x), ratio_component(P.y, Q.y))
```

This is a finite-input interpretation with single-precision arithmetic. The
fallback 10 applies to small denominators; it is not a cap on every ratio.

For **A at brain `+0x518`**, each eligible subject from list `+0x280..+0x288`
contributes a position- and age-weighted ratio against the self record. That
contribution is divided by the sum of the same subject's ratios at the self
position and eligible support positions:

```text
h0 = R(weighted_P(subject, self_position), Q(self))
H  = h0 + sum_over_support R(weighted_P(subject, support_position), Q(self))
if H > 0:
    A += (h0 / H) * h0
```

The denominator uses **the self Q pair for every support position**, an easily
missed detail. For **B at brain `+0x51C`**, the code combines self and eligible
support P pairs, then compares them with the sum of the opposing-list Q pairs:

```text
B = R(P(self) + sum_over_eligible_support P(support),
      sum_over_eligible_opposing_subjects Q(subject))
```

The exact bit filters are in the manifest; the support set used in A differs
slightly from B because B also excludes records with flag bit 4 set.
“Opposing” and “support” are candidate interpretations of the list/filter roles,
not recovered names for their complete membership rules.

Game `0x876F60` weights the subject's P pair using:

- A distance-like helper of the XY displacement, divided by subject `+0x50`,
  producing the factor `2 - min(distance/range, 2)`.
- An age factor `1 - clamp(convert_counter(now-timestamp)/60, 0, 1)`.

The range is obtained through the equipment path or a scaled fallback.
Clock units and zero-range behavior remain open. Do not turn the constant 60
into a claim about seconds without tracing the conversion globals.

There is additional evidence about the pairs' origins. `0x878740` gets P from
an equipment/object helper or a cached component pair. It gets Q through
`0x8136E0`; for a human, that routine queries **`Human::eParams_Health`**,
uses the resulting value as its first component and zero as its second.
Other entities use a pair from a classification table.

Thus “relative incoming pressure” for A and “relative self/support capacity”
for B are useful working interpretations. Their exact two-component meaning,
units and classification rules still need static tracing. They are not merely
counts of nearby enemies and friends.

## A named link to morale

RTTI identifies game vtable `0x10FF320` as
**`Scene::Stats::eMoraleProcessor`**. Its primary slot 4 is `0xA5A490`.
That method handles numeric event types 3 and 5 and calls brain virtual byte
offset `0xE8`, which is slot 29. In `Actor::eHumanBrain`, slot 29 is the
already-reviewed `0x945010`, which updates the bounded scalar at `+0x474`.

This gives a strong static association between S and morale, beyond guessing
from its 0–100 range. The complete event meanings, distribution to nearby
actors, and interaction with health still need review. It is not a complete
model of morale or suppression.

## From a state value to actual orders

Game `0x9538A0`, corresponding to editor `0x7DAED0`, reads the brain through
context `+0x30` and selects a movement direction and action code. In the branch
where brain flag bit 6 is clear, the reviewed relationships are:

| Brain state | Selected action code and label | Additional conditions |
|---|---|---|
| 0 | 3, `retreat`; or 8, `rush_back` | Helper `0x902980` can select the latter |
| 1 | 8, `rush_back` | Other caller/path gates still apply |
| 2 | Return without this movement attempt | This does not mean the actor does nothing elsewhere |
| 3 or 4 | 2, `advance`; or 7, `rush_ahead` | Requires equipment/target checks; compares target distance with equipment helper `0x80A910` |

These **action codes differ from brain state codes**. Their names have a direct
code connection: `0x9545F0` indexes the pointer table at `0x1482E40`, appends
`_to_cover` or `_move`, passes the label onward, and records the action code
at context `+0x3DC`. That table is initialized in writable `.data`, so these
are its values in the executable, not a claim that nobody can change them.

The movement routine attempts a cover candidate through `0x951210`. On a
successful branch, it constructs an **`eComplexOrder`** and links:

```text
Order::eMovementChange -> Order::eMoveToCover -> trailing context order
```

The cover factory call is at `0x9541D7`. The fallback path can instead create:

```text
Order::eMovementChange -> Order::eMove -> trailing context order
```

The movement factory call is at `0x95448A`. These order identities are supported
by factory/constructor code and independently checked RTTI vtables. The
compound-order helper `0x912370` invokes brain slot 13 to install the new order
when it differs from the current one. Child insertion passes through
`0x900A60`. The full ownership and validation contracts remain open.

There are additional gates, timers, geometric checks and failure branches.
The table describes a concrete path from state to orders; a state value alone
does not guarantee that a soldier will successfully perform that action.

### A tempting name table remains provisional

Both binaries contain an identical five-entry table:
`flee=0`, `retreat=1`, `none=2`, `advance=3`, `charge=4`, adjacent to human-brain
data. Its game/editor RVAs are `0x10EC720` / `0xF51FC0`.

However, this pass found no Ghidra references to either table start and no
absolute pointer to the game table. Proximity and matching values are not
enough to establish its live association with brain `+0x52C`. The manifest
therefore records it separately from the directly observed action labels.
Further static investigation may establish the link; it is not automatically
a runtime-only question.

## What runtime would add

Static work can still recover subject classification, pair-value origins,
cover scoring, callback scheduling and more downstream order validation.
The member-displacement scan is not exhaustive: adjusted pointers, bulk
accesses, indirect calls and code Ghidra has not disassembled can hide uses.

A later controlled runtime scenario would establish the actual input values
and list contents, which gated path executes, whether the engine accepts its
orders, callback cadence/thread, and object lifetime. These are useful checks
before replacing decision policy. They are not prerequisites for gathering
the static evidence above.

## Reproduce and verify

Examples below run from the repository root with `GOH_BINARIES` as described
in the README. Run commands sequentially against the shared Ghidra project.

```sh
python3 research/scripts/run_headless.py --build-id 25492057 members --program call_to_arms.exe --offset 0x518 --offset 0x51c --offset 0x52c --offset 0x474 --offset 0x508 --offset 0x50c --offset 0x464 --output local-work/member-scans/build-25492057/call_to_arms.json
python3 research/scripts/run_headless.py --build-id 25492057 members --program call_to_arms_ed.exe --offset 0x518 --offset 0x51c --offset 0x52c --offset 0x474 --offset 0x508 --offset 0x50c --offset 0x464 --output local-work/member-scans/build-25492057/call_to_arms_ed.json
python3 research/scripts/run_headless.py --build-id 25492057 export --program call_to_arms.exe --candidates research/artifacts/build-25492057/call_to_arms.flow-pass.tsv --anchors research/artifacts/build-25492057/call_to_arms.flow-anchors.tsv --output local-work/exports/build-25492057/call_to_arms-flow
python3 research/scripts/run_headless.py --build-id 25492057 export --program call_to_arms_ed.exe --candidates research/artifacts/build-25492057/call_to_arms_ed.flow-pass.tsv --anchors research/artifacts/build-25492057/call_to_arms_ed.flow-anchors.tsv --output local-work/exports/build-25492057/call_to_arms_ed-flow
python3 research/scripts/verify_fine_map.py --map research/artifacts/build-25492057/flow-map.json --binaries-dir "$GOH_BINARIES" --exports-dir local-work/exports/build-25492057 --output research/artifacts/build-25492057/flow-validation.json
```

All 33 game and 15 editor requested entries were exact Ghidra function entries.
The focused exports decompiled 61 game / 43 editor functions. The two tiny input
bridges are deliberately tracked separately, rather than pretending Ghidra
had recognized them as functions.

[flow-validation.json](../artifacts/build-25492057/flow-validation.json) records
binary and export hashes plus checks of constants, tables, RTTI, bridge bytes,
and instruction evidence locations. Those checks do not prove semantic names
or runtime completeness. Decompiled bodies and full member scans remain local.
The six PE scanner tests passed; negative checks rejected a wrong RTTI slot,
action label, bridge byte sequence, and enum value. The earlier fine map also
passed the extended verifier.
