# Fine-grained brain mapping — build 25492057

This pass maps **individual predicates, fields, setters, and inlined state
transitions** beneath the initial actor/brain dispatch map. Analysis is static
against the exact game/editor hashes in [fine-map.json](../artifacts/build-25492057/fine-map.json).
Names below describe observed roles; they are not recovered source symbols.
No runtime hooks or SDK offset definitions have been changed.

The subsequent [input-to-order trace](flow-map-25492057.md) identifies the A/B
producer, establishes a named morale association for S, and follows selected
state branches into movement/cover orders. Statements of unresolved meanings
below describe this initial fine-grained pass; see that follow-up for progress.

## Mapping grain

A useful mapping unit is the smallest behavior we can explain with evidence.
It can be a whole function, a virtual dispatch, an inlined branch, one flag,
or a state transition. A function boundary is not a limit on the map's detail.

For each unit, record its input fields and units, conditions and thresholds,
writes, calls and side effects, game/editor correspondence, evidence instruction
RVAs, and remaining uncertainties. Unknown meanings stay numeric. Replacing
decision policy will require preserving reference ownership, order processing,
and other engine bookkeeping until those contracts are understood.

The exporter now records function body ranges, basic blocks, and outgoing flow
edges in addition to calls and assembly. These expose branches inside large
methods; they do not imply that every exported block has been understood.

The command path also uses `-1` as an unchanged-field sentinel.

## Small functions with observable contracts

### Movement mode setter: game `0x903140`, editor `0x7896B0`

The complete-brain pointer is in RCX and an integer input in EDX in the reviewed
machine code. This observation is not a ready-to-use SDK declaration.

When the extracted current mode differs from the **unmasked** input, it:

1. Replaces only bits 12–13 of brain `+0x398` with the masked input.
2. If that masked value is `zone=2`, copies eight bytes from owner actor `+0x74`
   to brain `+0x128`, a candidate movement-zone position anchor.
3. If the context pointer at brain `+0xE0` exists, calls game `0x912520` on its
   nonnull `+0x28` pointer with argument zero, then clears that pointer.

The copy is at game `0x90317F`/`0x903184`; cleanup and clearing are at
`0x9031A3`/`0x9031A8`. Directly patching the bit field would skip those side
effects. Context type and cleanup ownership remain unresolved.

The separate speed setter, game `0x9031C0` / editor `0x789730`, updates bit 14
when its extracted value differs from the input. Its reviewed body has no calls.

### Boolean predicates

These return a boolean in AL; Ghidra's wider inferred return types are not
evidence that the rest of RAX is meaningful. `F[n]` below means bit `n` of the
brain flags at `+0x39C`. Owner flags use different addresses explicitly shown.

| Game entry | Exact condition for true |
|---|---|
| `0x902950` | `control==user` and owner dword `+0xDB4` bit 17 |
| `0x902AD0` | brain pointer `+0x100` exists, its pointer `+0xA8` exists, and that pointer differs from the brain's owner pointer |
| `0x905BE0` | brain pointer `+0x1F8` exists, or brain pointer `+0x100` exists with a nonnull pointer at its `+0x1C8` |
| `0x942D10` | `F[9]` and `0x902AD0()` and `follow_commander` and not `0x902950()` |
| `0x942C10` | owner dword `+0x1C0` bit 28 clear; if movement is `hold`, require the conditions of `0x942D10`; finally reject `control==user && F[28]` |
| `0x942CB0` | movement is neither `hold` nor `zone`, control is `AI`, `F[6]` clear, signed state at `+0x52C` greater than 2, and not `0x905BE0()` |

This identifies precise gates while leaving unnamed bits and pointee types
unresolved. The last predicate is a candidate advance-eligibility check, not
yet a proven attack/advance command. Do not simplify its movement test to
`free`: the two-bit field also admits unnamed bit pattern 3.

## One inlined decision block, down to thresholds

The human slot-35 method, game `0x941D00` / editor `0x7C9290`, contains a
state selection region followed by other work. For this region define:

| Symbol | Brain field | What is known |
|---|---|---|
| `A`, `B` | floats `+0x518`, `+0x51C` | Inputs; their producers and gameplay meanings remain unknown |
| `S` | float `+0x474` | Constructor initializes 100; slot 29 adds a delta and clamps to 0–100 for finite inputs |
| `state` | int32 `+0x52C` | Constructor initializes 2; reviewed paths write codes 0–4 |
| `deadline` | uint32 `+0x530` | Nonzero value temporarily bypasses state selection |
| `Ra`, `Rr` | floats `+0x524`, `+0x528` | Named advance/retreat ratios |

The code computes `Ta = (A * Ra) * k` and `Tr = (B * Rr) * k`, where
`k=1.5` if the integer at `owner->component_0xDC0 + 0x24` is 1 or 2,
otherwise `k=1`. That component field's meaning is unresolved.

The following is analyst pseudocode for ordinary finite arithmetic, with
single-precision operation order understood. It does not model NaNs or all
machine-level conversion edge cases. `finish_region` continues the same method.

```text
if deadline != 0:
    if uint32(now) >= deadline:
        state = 0
        deadline = 0
    goto finish_region                 # also skips selection on expiry

if state == 0:
    if B * Rr >= A:                     # deliberately does not use k
        add_to_S(5)                    # virtual slot 29
        state = 2
    else if S > 50:
        sample = next_random_sample()
        state = 3
        deadline = uint32(now + convert_duration(1 + sample))
    goto finish_region

state = 2
if S > 70 and not no_advance and B > Ta:
    state = 4 if B > 2 * Ta else 3

if not no_retreat:
    if A > Tr or S < 30:
        state = 0
    else if S < 50:
        state = 1

finish_region:
    continue with target/component updates and base-brain work
```

The ordering matters: the retreat-named branch can override the advance-named
branch. The state-zero branch does not test either disable byte. Therefore the
names `no_advance` and `no_retreat` alone do not mean a complete ban on every
transition that might later lead to those actions.

For finite arithmetic, equality at `S=70` does not enter the advance branch;
`B=2*Ta` selects 3 if its earlier gates pass. In the retreat branch with
`A<=Tr`, `S=30` selects 1 and `S=50` retains the preceding selection.
The numeric states have **not** been named attack, cover, flee, etc.

These are instruction spans within functions, not independent callable entries.

### Randomness and the second timer

The random path advances a uint32 state using
`new = old * 0x7FF8A3ED + 0x2AA01D31` modulo 2^32, increments a counter,
and forms a float from `(new >> 8)` times the mutable global at game RVA
`0x1587C54`. That global is outside file-backed data. Its initialization has
not been traced, so no normalized range is asserted.

Game `0x65E700` reads the mutable counter at `0x1556E48`.
`0x65E730` multiplies a float duration by the mutable value at `0x14776C8`
and truncates to integer. We have not established the units or multiplier;
the delay must not yet be described as a number of seconds.

A separate deadline at brain `+0x478` gates recovery of `S`. Human slot 29,
game `0x945010` / editor `0x7CC510`, clamps `S+delta`; a negative delta also
sets this deadline to `now+convert_duration(10)`. After calling the base-brain
method, slot 35 adds `(0.5*100)/120` through slot 29 if its recovery deadline
allows, then sets `now+convert_duration(0.5)`. This establishes numeric
recovery behavior without assuming that `S` is morale, health, or suppression.

## Target selection and engine bookkeeping

Game helper `0x943560` refreshes a reference at brain `+0x3D0`, snapshots
`+0x3B8` into `+0x3B0`, clears byte `+0x3DA`, calls `0x9437A0`, and assigns
the returned reference to `+0x3B8`. The caller compares the old/new references,
conditionally calls `0x944070`, then releases the old snapshot. Reference
counts and conditional destruction are visible in assembly.

In the editor, the corresponding refresh and snapshot work is **inlined into
`0x7C9290`**, which calls picker `0x7CAD70` and change helper `0x7CB5A0`.
This is why correspondence must sometimes match operations within functions.

The picker has an initial global gate and favors a nonnull `+0x3D0` reference.
Otherwise it filters entries from the owner's component at `+0xDD0`, using its
pointer range `+0x280..+0x288`. Named diagnostic strings include `not suitable`
and `broken`. The list passes to game `0x9136E0`; then an object initialized
through `0x957C00`/`0x957C70` supplies a further per-candidate check. The code
returns the first passing candidate, or falls back to the first list entry.
The suitability, ranking, and checking internals are the next frontier; a
returned reference is not yet established as a valid firing target.

The change helper obtains another component, conditionally releases/reset a
nonnegative handle at brain `+0x3E4`, and may acquire a replacement when the
new target has bit 25 at `+0x10`. The component/resource type is unresolved.

Separately, brain slot 24, game `0x905710` / editor `0x78BE20`, processes
orders: it calls the current order's slot 3, brackets that callback with brain
flag bit 24, conditionally cleans up orders, and processes due 16-byte entries
from the delayed queue at `+0x98..+0xA0`. This refines the original dispatcher
map: reconsidering decisions and progressing orders are separate calls with
different side effects. Their complete lifecycle and reentrancy remain open.

## Reproduction and checks

Run the focused exports after importing the programs as described in the
[README](../../README.md). They are read-only and skip autoanalysis.

```sh
python3 research/scripts/run_headless.py --build-id 25492057 export --program call_to_arms.exe --candidates research/artifacts/build-25492057/call_to_arms.fine-pass.tsv --output local-work/exports/build-25492057/call_to_arms-fine

python3 research/scripts/verify_fine_map.py --map research/artifacts/build-25492057/fine-map.json --binaries-dir "$GOH_BINARIES" --exports-dir local-work/exports/build-25492057 --output research/artifacts/build-25492057/fine-validation.json
```

The game export contains 50 functions / 1,052 basic blocks; editor 39 / 826.
All 26 game and 15 editor requested entries are exact Ghidra function entries,
and every selected decompilation completed. Many blocks are support code or
remain unreviewed. These counts are not a percentage of AI coverage.

The verifier checks both binary fingerprints, eight enum tables, 18 read-only
float constants, reviewed method entries, and recorded instruction starts
against function body ranges. [fine-validation.json](../artifacts/build-25492057/fine-validation.json)
records results and report hashes. It checks evidence locations and raw data,
not the truth of every semantic interpretation. Full listings and decompilation
remain local and untracked.

The six existing PE scanner tests passed. Negative checks also confirmed that
the verifier rejects an incorrect binary hash, enum value, constant, and an
address inside an instruction. Independent LLVM objdump listings agree with
Ghidra's instruction starts for the two state-selection spans and the game
movement setter, accounting for LLVM printing `LOCK` prefixes separately.
